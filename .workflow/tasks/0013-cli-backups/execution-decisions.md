# Backup execution decisions

Last Edited: 2026-10-03

- D1 (tradeoff): publish a backup as one uniquely named directory containing budget.zip and manifest.json. Stage and flush both files, verify completion, then rename the directory. Two independently renamed sibling files could expose a mismatched pair. No existing artifact is overwritten. Confidence: high. Additive CLI artifact format; archive contents remain canonical Actual zip. Relationship: aligned. Review: pending independent review.
- D2 (underspecified choice): the manifest has schemaVersion 1 and explicitly declares encrypted false, sourceEncrypted, remoteFreshness, checkpoint, pending count, and validation not-imported. Creation proves file completion and hash, while subsequent isolated import validation remains a separate operation. The alternative treating source encryption as artifact protection would be incorrect. The encrypted fixture confirms plaintext ZIP bytes and source identity. Confidence: high. No invented encrypted archive. Relationship: aligned. Review: pending independent review.

- D3 (tradeoff, 2026-10-03): validation runs public importBudget and queries in a child process with a fresh private directory, no server configuration, and no inherited ACTUAL variables. Importing into the caller's cache could overwrite the archive's original ID. A bounded worker permits termination and cleanup before returning. Confidence: high. Additive CLI lifecycle ownership; archive interpretation remains in core. Relationship: aligned. Review: pending independent review.
- D4 (underspecified choice, 2026-10-03): return normalized public domain fingerprints, row counts, and engine-calculated account balances. Queries include deleted rows and all split rows, paginate in 1000-row batches, and use deterministic ordering. Tags use getTags. The alternative duplicating SQL or balance formulas in CLI would bypass canonical owners. The rich encrypted fixture compares source and imported snapshots, including rules, schedules, allocations, reservations and cashPlanning preferences. This is domain-read verification, not a claim of exhaustive SQLite integrity validation. Confidence: high for the named domains. Relationship: aligned. Review: pending independent review.

- D5 (plan deviation, 2026-10-03): correct nested teardown ordering in existing core main.test.ts after broader verification exposed EBUSY and EEXIST on Windows. Close the budget before deleting its fixture. Leaving this unresolved would retain an observed failure; changing production database code would address the wrong owner. Eight focused tests now pass. Confidence: high. Test-only change, reversible. Relationship: extends verification cleanup beyond the proposed CLI files. Review: pending independent review.

- D6 (design wall, 2026-10-03): ordinary importBudget reuses the archive's ID and can replace its original cache. Add public restoreBudget and a canonical importActual/importBuffer new-name path instead of rewriting ZIP contents or copying budget files in CLI. The core generates a new ID, exclusively creates its directory, and reuses newBudgetMetadata for clone/restore identity reset. A failed exclusive mkdir never permits cleanup of an existing directory. Invalid SQLite cleanup removes only the restore-owned directory without reopening the invalid database. Alternatives: private import plus clone and export, or a CLI file copy, would require extra archive transformations or bypass lifecycle ownership. Confidence: high. Additive public API; default import behavior retains its ID semantics. Relationship: aligned with the plan's missing-capability extension. Review: pending independent review.
- D7 (underspecified choice, 2026-10-03): backups restore requires --offline and a unique name. It validates in the isolated worker before initializing the destination, then holds the lifecycle lock through engine shutdown. Cancellation can stop validation or prevent writing after lock acquisition; once writing starts, the engine completes or cleans up. If final inspection fails after creation, return partial completion with the new ID rather than delete a committed copy or invite blind retry. Confidence: high. Existing source files and remote identities are preserved. Relationship: aligned. Review: pending independent review.

- D8 (underspecified choice, 2026-10-03): comparison takes two explicit local IDs and requires offline mode. Public export and isolated import produce domain fingerprints and canonical account balances. Observations occur separately and disclose unknown remote freshness and jointSnapshot false. Stable IDs match accounts; missing accounts and differing currencies produce null deltas. Name-based matching or duplicate finance formulas would introduce unsupported semantics. Confidence: high. Read-only and additive; no source ledger or remote changes. Relationship: aligned. Review: pending independent review.
- D9 (tradeoff, 2026-10-03): retention keeps the requested positive number of newest valid artifacts per source identity. Every eligible archive passes isolated import before selection; corrupt, linked, and unmanaged directories remain untouched. Truncated inventory prevents deletion. A total deadline and shared root lock bound work and serialize cooperative creation/retention. Apply computes a fresh policy and rechecks all valid artifacts before deleting only budget.zip, manifest.json, and their empty directory. Recursive deletion could remove unrelated files; hash-only selection could discard the last usable backup. External filesystem writers are not covered by a distributed lock. Confidence: high for the tested cooperative boundary. Explicit apply is reversible only from another copy; partial failures report deleted and active paths. Relationship: aligned. Review: pending independent review.
- D10 (design wall, 2026-10-03): move stableJson from the API-dependent snapshot module to pure CLI utils. Retention needs deterministic manifest comparison without importing the API runtime. A focused filesystem failure test exposed the transitive browser platform dependency. Mocking the API would conceal the dependency problem. Confidence: high. Internal helper relocation preserves serialization; shared cancellation handling also moved to the validation owner. Relationship: extends internal dependency cleanup within the new modules. Review: pending independent review.
