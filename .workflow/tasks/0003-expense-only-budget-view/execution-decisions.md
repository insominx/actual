## D6 — Safe Request Handling During Handover

- Trigger / category: user requested continuation of the remaining handover gap; the normal-UA browser regression reproduced a hanging `load-prefs` request issued immediately after promotion. Contract extension and safety tradeoff, implemented as a separate coordinator slice.
- Confirmed mechanism: the client connection's initial queue is already disabled after its first connection. The coordinator forwarded new requests while the replacement worker had no handlers or was still restoring its database. Election also silently cleared outstanding reply routes.
- Decision / authority: the existing coordinator readiness state owns a per-group FIFO for unsent messages. Flush only after both backend connection and restore succeed, and only for ports still in that group. Explicitly reject outstanding requests on election; never replay a write whose previous outcome is unknown. Reuse `postErrorReply` for ordinary, `catchErrors` and `api/` response envelopes.
- Alternatives: arbitrary browser delays or retries would mask the race. Replaying pending writes risks applying financial mutations twice. Adding a second bridge/client queue would duplicate the coordinator's budget/readiness authority. Acknowledged exactly-once replay is a different protocol and is not introduced here.
- Failure / disposal policy: reject queued/future work if initialization or restore fails; reject or discard work for closed, detached or evicted tabs. Error codes are `backend-restarted`, `backend-unavailable` and `budget-detached`. Callers must reconcile an interrupted write's actual ledger outcome before retrying it. Initialization-failure acknowledgement remains a control message that reaches the unavailable worker, preserving its retry-stop protocol.
- Evidence / confidence: high. Nine initial failing-first coordinator cases isolated queueing, interrupted envelopes and failed restoration; an additional red eviction test caught a late-write hazard before adding the membership guard. The strengthened browser test issues both a read and a write during promotion rather than waiting for backend reconnection.
- Scope / reversibility: coordinator source/tests, strengthened multi-tab e2e and smoke evidence, plus a separate handover release note; no storage migration, accounting change, automatic mutation retry or bridge API change. Working queues and request metadata die with their group. Independent review pending; D5's handover limit is superseded by this verified slice.

## D5 — Cross-Tab Follow-Up

- Trigger / category: user requested continuation; reproduced D4 twice and isolated a coordinator registration bug. Separate bugfix slice extending the original feature scope, not a change to expense accounting.
- Decision: reconcile every successful `load-prefs` reply with the worker's actual budget ID, using the existing `handleBudgetLoaded` owner. Notify each port of its updated role/budget without creating another worker.
- Alternatives / evidence: limiting migration to `__creating-` misses creation/import in the lobby and replacement by an existing leader. Four new failing-first cases proved those omissions; the original 44 coordinator tests were green. Changing SQLite, delaying tab opening or forcing direct workers would mask the cause instead of fixing registration.
- Confidence / impact: high. Production smoke changed from two independently writing groups and a malformed-database error to one leader plus one follower with edit/undo delivered to both. Registry and bridge associations are working state; no persistence or worker API change. This prevents the reproduced error but does not repair previously corrupted databases.
- Contract / scope: one backend per open budget after creation/replacement; existing multi-budget routing, disposal and expense inclusion remain intact. Changes are coordinator source/tests, a normal-UA two-tab browser test, smoke evidence/exit status and a separate bugfix release note.
- Review: pending independent review. D4 is historical; its cross-tab edit/undo gap is closed by this follow-up. Remote-server sync remains unverified. Requests issued during backend handover remain outside this fix; the browser regression waits for the backend's reconnection signal before proving resumed edits.
