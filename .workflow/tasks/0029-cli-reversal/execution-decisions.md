# Execution decisions: 0029 cli-reversal

| ID  | Decision                                                                                                                                                                                                                                                                                                                                                                               | Reason                                                                                                         | Status                           |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| D1  | Start on Linux acceptance of the prerequisites (Windows reruns open).                                                                                                                                                                                                                                                                                                                  | Same rule as the other dependents.                                                                             | ASSUMPTION for Michael to review |
| D2  | A reversal is a new guarded change of an existing operation (`transactions.categorize`, `budgets.move`, `cash-planning.save`) under a new operation ID, prepared and applied by the shared executor. No new core handler or receipt format is added; the receipt of the reversal is a normal receipt of that operation, and the CLI result links it with `reverses`.                   | Plan: reversal is a new compensating operation with its own receipt; do not invent per-domain receipt formats. | Adopted                          |
| D3  | Postconditions are checked in the CLI by comparing the freshly prepared inverse proposal (engine-produced before-values) with the original receipt's after-values; the engine's own staleness check then guards the window between prepare and apply. Conflicts are `STALE_PREVIEW` with a `conflicts` list; engine refusals (for example a row reconciled since) are `INVALID_INPUT`. | Reuses core-owned proposals instead of a second set of core postcondition handlers.                            | ASSUMPTION for Michael to review |
| D4  | Categorization reversal requires every changed row to have had the same prior category; mixed batches are refused with guidance to reverse each group explicitly.                                                                                                                                                                                                                      | One reversal must be one atomic guarded change; splitting it into several would not be atomic.                 | ASSUMPTION for Michael to review |
| D5  | Allocation reversal is the opposite move of the same amount in the same month, allowed only while both categories still hold the budgeted amounts the move left; it never passes `allowOverspend`, so a destination that spent the money cannot give it back.                                                                                                                          | Plan A1/A2: restore without overwriting later edits.                                                           | Adopted                          |
| D6  | Cash plan reversal restores the earlier saved plan (or clears it when there was none) only when the saved plan still equals what the change saved and the earlier plan restores byte-for-byte after today's validation. `set-target`, `reset-target` and `reset` are `cash-planning.save` receipts, so they are reversible too.                                                        | Avoid silently rewriting a plan that validates differently today.                                              | Adopted                          |
| D7  | Merges, deletions, imports, added rows, reconciliation finishes, payee merges, lifecycle operations, uncertain receipts and unapplied receipts are not reversed. The refusal states the reason and lists backup recovery: `backups list`, `backups restore` into a new local budget, `budgets compare`, then explicit changes.                                                         | Plan: no universal undo and no automatic in-place restore.                                                     | Adopted                          |
| D8  | "Recovery diagnose" is `changes inspect <operation-id>` (state, meaning, next steps, reversal plan), not a separate command; it reads the local journal only.                                                                                                                                                                                                                          | One read surface for a receipt.                                                                                | ASSUMPTION for Michael to review |
| D9  | `capabilities.reversal` in discovery is `true` for `transactions.categorize`, `budgets.move` and the `cash-planning` save commands, and `false` elsewhere.                                                                                                                                                                                                                             | Discovery should not fabricate reversal support.                                                               | Adopted                          |
