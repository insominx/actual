# Execution decisions: 0032 cli-automation

| ID  | Decision                                                                                                                                                                                                                                                                                                                                                                      | Reason                                                                                                                         | Status                                                       |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| D1  | Start on Linux acceptance of 0030 and 0031 (Windows reruns open).                                                                                                                                                                                                                                                                                                             | Same rule as the other dependents.                                                                                             | ASSUMPTION for Michael to review                             |
| D2  | Jobs live in the CLI (`src/jobs.ts`, `commands/jobs.ts`) and run the 0031 intake workflow (`createRun`/`advanceRun`); each import is the existing `imports.file` guarded change. No core or API change.                                                                                                                                                                       | Plan: run-once entry over the workflow runner; no second import path.                                                          | Adopted                                                      |
| D3  | A job supports only the `intake` workflow and the `imports.file` mutation, which must be listed explicitly (`--allow imports.file`). Read workflows such as `workflow weekly-checkup` can be scheduled directly.                                                                                                                                                              | Plan: jobs bind explicit allowed mutations; intake is the only file-driven workflow.                                           | ASSUMPTION for Michael to review                             |
| D4  | A file is stable when it has not been modified for `--stable-seconds` (default 30) and is not named like a temporary download (`.part`, `.partial`, `.tmp`, `.crdownload`, `.download`). Unstable files stay in the inbox as `pending-unstable`.                                                                                                                              | Plan A1: partially written files remain pending; a modification-age rule works for cron-style runs without a resident watcher. | ASSUMPTION for Michael to review                             |
| D5  | Deduplication key: SHA-256 of the content plus account plus settings (stable JSON), kept in a per-job ledger (`jobs/<name>/state.json`). A repeated file moves to processed as `duplicate` without an import. The same content routed to another account stays in the inbox as `cross-account-review` unless the job has `--allow-cross-account`.                             | Plan A1.                                                                                                                       | Adopted                                                      |
| D6  | Routes are regular expressions on the file name, first match wins. A file with no route stays in the inbox as `no-route`; the job never guesses an account.                                                                                                                                                                                                                   | Plan: unknown or new choices stop for review.                                                                                  | Adopted                                                      |
| D7  | Inbox, processed and error must be distinct, non-nested directories fixed at creation. Committed imports move to processed, failed imports to error, and files whose import never ran stay in the inbox. Name collisions get a run-ID or `duplicate` prefix.                                                                                                                  | Plan: move files only within declared directories.                                                                             | Adopted                                                      |
| D8  | Overlapping invocations: a per-job lock (the existing `lock.ts` gate, about a one second wait) admits one run; the other fails with retryable `ENGINE_FAILURE` (`reason: job-active`). The active run ID and its files are recorded before the run starts, and the next `jobs run` resumes that run before scanning again, replaying interrupted imports from their receipts. | Plan A2.                                                                                                                       | Adopted                                                      |
| D9  | `jobs disable` stops future runs and cancels a paused or failed active run, moving its committed files; `jobs enable` re-enables. `--dry-run` previews each ready file with `previewFileImport` and reports planned moves without writing anything.                                                                                                                           | Plan A3.                                                                                                                       | Adopted                                                      |
| D10 | Alerts are local JSON results under `jobs/<name>/results/`, referenced by `jobs status`; there is no external delivery. `jobs schedule` prints cron, systemd timer and Windows Task Scheduler recipes and installs nothing. The Linux check runs the printed command arguments; the Windows recipe is not executed here.                                                      | Plan: local artifacts unless the user configures delivery; scheduler examples.                                                 | ASSUMPTION for Michael to review (Windows execution pending) |
| D11 | Job records hold no credentials; the server password or session comes from the environment or a profile at run time.                                                                                                                                                                                                                                                          | Plan: never store credentials in receipts or run records.                                                                      | Adopted                                                      |
