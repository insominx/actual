# Execution decisions: 0019 cli-transfers

| ID  | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Reason                                                                                                        | Status                           |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| D1  | Start on 0018's Linux acceptance (Windows rerun open).                                                                                                                                                                                                                                                                                                                                                                                                                | Same rule as the other dependents.                                                                            | ASSUMPTION for Michael to review |
| D2  | Candidates are unlinked, non-parent, non-starting-balance rows in different live accounts whose amounts cancel exactly, at most `--days` apart (default 3, maximum 31). Rows already carrying a transfer payee are excluded and surface in `inspect`/`check`. Ambiguity is any leg with more than one candidate; it is reported, never resolved.                                                                                                                      | Matches the client's `validForTransfer` rule plus a date window; no fuzzy amounts.                            | ASSUMPTION for Michael to review |
| D3  | `transfers create` is not a separate command: a new transfer is a guarded `transactions add` with the destination's transfer payee, and the engine creates the counterpart.                                                                                                                                                                                                                                                                                           | One creation path through the engine's transfer owner.                                                        | ASSUMPTION for Michael to review |
| D4  | Match refuses split parents and children (split transfers are set on a child's payee through `transactions split`), legs that are already linked, and rows with an unlinked transfer payee (use repair). Reconciled rows need `allowReconciled`. Each leg keeps its own date.                                                                                                                                                                                         | The client's link action has the same shape; split transfers have engine rules of their own.                  | ASSUMPTION for Michael to review |
| D5  | Matching writes both links in one batch with transfer creation off, the same way the client's "make transfer" action does, so no counterpart is created. Categories are cleared only when the engine's own rule (`transferClearsCategory`) says so; a budget-boundary match keeps the on-budget category. Unmatch clears both payees (a transfer payee without a link would be relinked on the next edit) and deletes nothing; the receipt keeps the previous payees. | No duplicate money movement; follows the engine category rule rather than the client's always-clear shortcut. | ASSUMPTION for Michael to review |
| D6  | Card payments are internal transfers: Actual has no credit-card account type, so they are classified by on/off-budget like any other account. Cash-planning parity holds because cash planning sums on-budget balances, which matching never changes; the packaged test checks the same on-budget totals.                                                                                                                                                             | Classification must come from ledger facts, not names.                                                        | ASSUMPTION for Michael to review |
| D7  | Repair is chosen by inspection: `unlink` for missing, non-reciprocal or same-account links (this row only), `resync` (engine linked transfer update) when the link is reciprocal but amount or payee drifted, and `relink` (engine transfer creation, adds one row) for a transfer payee without a link.                                                                                                                                                              | Uses the engine's transfer owner for every write that touches the counterpart.                                | ASSUMPTION for Michael to review |
