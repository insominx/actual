| D1  | Start on Linux acceptance of 0021, 0022, 0023 and 0027 (Windows reruns open).                                                                                                                                                                                                                                                                                                          | Same rule as the other dependents.                                                                  | ASSUMPTION for Michael to review |
| D2  | Core `server/checkup/data-quality.ts` owns the checks (one read handler `api/checkup-data-quality`); transfer findings reuse the 0019 transfer audit rather than a second definition.                                                                                                                                                                                                  | Keep calculation authority in core and reuse existing owners.                                       | Adopted                          |
| D3  | Duplicate candidates: top-level, non-transfer, non-starting-balance rows in one account with the same amount within a window (default 3 days, 0 to 14); two rows with different bank import IDs are never paired; each pair is one `info` finding marked heuristic.                                                                                                                    | The primary risk is false confidence, so the heuristic is narrow and labeled.                       | ASSUMPTION for Michael to review |
| D4  | Uncategorized covers on-budget leaf rows without a category, excluding transfers between two on-budget accounts (which never take one) and starting balances; off-budget rows are never flagged. Rows in a deleted category get their own `deleted-category` finding.                                                                                                                  | Matches the engine's categorization rules.                                                          | Adopted                          |
| D5  | Statement evidence is device-local (`statement-evidence.json` in the CLI data directory, keyed by sync ID or budget ID), user-declared, optionally linked to an import receipt operation ID, and passed to core on each checkup. It is labeled "user-declared, not bank-verified" in every result. Account IDs in evidence are checked when the checkup runs, not when it is recorded. | Plan slice 2: device-local evidence without fabricating bank verification; recording works offline. | ASSUMPTION for Michael to review |
| D6  | Coverage per account and month is `observed`, `statement-verified`, `discrepancy` or `unknown`. Observed rows are never called verified, and a month with no rows is `unknown` unless a no-activity statement (or a matching balance) covers it. Ledger balance for a statement is the sum of top-level rows through the month end.                                                    | Plan A2.                                                                                            | Adopted                          |
| D7  | Closed accounts are skipped unless named in `--accounts`.                                                                                                                                                                                                                                                                                                                              | Closed accounts would otherwise report every later month as unknown.                                | ASSUMPTION for Michael to review |
| D8  | Findings are bounded (`--limit`, default 200, maximum 500, with `truncated` and `totalFindings`) and each finding lists at most 100 IDs. Remediation is a reference only (`suggested` operations with example commands); nothing is applied. Report completeness annotations already exist from 0027, so slice 3 adds only the remediation references.                                 | Plan: checks are read-only; remediation is separately previewed.                                    | Adopted                          |
| D9  | The evidence file has no cross-process lock; it is replaced atomically, so two concurrent writers can lose one entry but never corrupt the file.                                                                                                                                                                                                                                       | Device-local, low-contention metadata.                                                              | ASSUMPTION for Michael to review |
